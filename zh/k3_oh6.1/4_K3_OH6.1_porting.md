## 2. 添加定制方案

产品方案定制涉及以下核心代码仓库：

- `build`：添加构建白名单，主要修改文件为：
  - `subsystem_components_whitelist.json`
  - `compile_standard_whitelist.json`
  - `core/gn/ohos_exec_script_allowlist.gni`
- `vendor/spacemit`：进迭厂商定制适配目录
- `device/board/spacemit`：进迭厂商板级适配目录
- `device/soc/spacemit`：进迭厂商芯片适配目录
- `kernel/linux/linux-6.18`：进迭厂商内核
- `extension/k3`：K3 的 U-Boot、OpenSBI、ESOS 源码

添加定制方案通过以下两种方式实现：

- **通过修改现有方案进行定制**
  适用于在现有开发板基础上快速适配新的方案。K3 平台现有 `pico` 和 `com260` 两个方案，可通过修改其中的参数来支持新的开发板。

  - 适配流程简单，开发速度快。
  - 注意：新开发板的板号需与原开发板保持一致（例如，仍命名为 `pico`）。
- **通过添加全新方案定制**
  适用于需要完全独立配置的场景。

  - 前期需进行一定的适配工作。
  - 不会与现有开发板配置冲突，可灵活进行自定义和修改。

下面分别对两种定制方案的操作进行说明：

### 2.1 通过修改现有方案定制

#### 2.1.1 定制 U-Boot

K3 的 U-Boot 源码位于 `extension/k3/uboot-2022.10`，由板级脚本编译，无需向进迭时空索要 bin 文件：

- 构建入口：`device/board/spacemit/xxx/uboot/BUILD.gn`（`action("build_uboot")`）
- 构建脚本：`device/board/spacemit/xxx/uboot/build_uboot.sh`
- 板级补丁：`device/board/spacemit/xxx/uboot/uboot_patch/*.patch`

`build_uboot.sh` 的流程是：把 U-Boot 源码拷到 `out/uboot` → 依次打 `uboot_patch` 下的全部补丁 → `make k3_defconfig` → 裁剪 FSBL（关闭 `SPL_UFS`/`SPL_SCSI` 等）→ 编译 → 把产物拷到镜像输出目录。

编译产物及去向：

| 产物 | 去向 | 对应的打包配置 |
|------|------|----------------|
| `u-boot.itb` | `${OHOS_IMAGES_DIR}/u-boot.itb` | `genimage.cfg`、`partition_flash.json`、`partition_4M.json`、`fastboot.yaml` |
| `FSBL.bin` | `${OHOS_IMAGES_DIR}/factory/FSBL.bin` | 同上 |
| `bootinfo_spinor.bin` / `bootinfo_spinand.bin` / `bootinfo_block.bin` | `${OHOS_IMAGES_DIR}/factory/` | 同上 |
| `u-boot-env-default.bin` | `${OHOS_IMAGES_DIR}/env.bin` | `genimage.cfg`、`partition_4M.json` |
| `u-boot-spl.bin` | `${OHOS_IMAGES_DIR}/`（调试用） | — |

上述产物**全部在构建时生成，不回拷源码树**。源码树中与之相关的只有打包配置和启动环境文件，位于：

`device/soc/spacemit/k3/kernel/boot/`

```bash
|-- bootctrl.img
|-- bootfs
|   |-- bmp2ppm.sh
|   |-- boot_logo_spacemit_0.bmp
|   |-- boot_logo_spacemit_180.bmp
|   |-- boot_logo_spacemit_270.bmp
|   |-- boot_logo_spacemit_90.bmp
|   `-- boot_logo_zkhl_0.bmp
|-- fastboot.yaml
|-- genimage.cfg
|-- partition_4M.json
`-- partition_flash.json
```

各方案的 U-Boot 启动环境文件位于板级目录：

`device/board/spacemit/xxx/kernel/boot/bootfs/env_k3.txt`

```bash
// Common parameter
console=ttyS0,115200
init=/init
bootdelay=0
loglevel=1
knl_name=Image
default_boot_device=soc/c0e00000.ufshc
boothardware=pico
dtb_dir=
```

若某一方案需要专属的 U-Boot 行为，优先在 `device/board/spacemit/xxx/uboot/uboot_patch/` 下新增补丁（脚本会按文件名顺序自动应用全部 `*.patch`），而不是直接改 `extension/k3/uboot-2022.10` 源码。

```bash

./build.sh --product-name xxx --ccache --prebuilt-sdk
```

##### 2.1.2.2 修改 defconfig

内核的 defconfig 文件位于：

```bash
kernel/linux/linux-6.18/arch/riscv/configs/
|-- k3_bianbu_defconfig      # K3 方案编译时使用的配置
|-- k3_defconfig             # 精简配置，U-Boot 的 SPL 也用它
|-- k3_rt_bianbu_defconfig   # 实时版
`-- k3_acpi_defconfig.diff
```

方案编译使用的配置名由板级脚本指定，例如 `device/board/spacemit/pico/kernel/build_kernel.sh` 中：

```bash
export KERNEL_CONFIG_NAME=k3_bianbu_defconfig
```

`k3_bianbu_defconfig` 是所有 K3 方案共用的，修改后对所有 K3 方案生效。

如果只是针对某个特定方案的修改，需要通过 patch 的形式来修改，过程如下：

- 生成 patch：`fix.patch`
- 将生成的 `fix.patch` 放置于 `device/board/spacemit/xxx/kernel/kernel_patch` 中
- `device/board/spacemit/xxx/kernel/build_kernel.sh` 中打 patch，如下：

```bash
patch -p1 <${OHOS_SOURCE_ROOT}/device/board/${DEVICE_BOARD}/${DEVICE_NAME}/kernel/kernel_patch/fix.patch
```

> 说明：现有脚本中打补丁的顺序是先打通用补丁（`device/board/spacemit/kernel_patches/linux-6.18/`），再打板级补丁（`device/board/spacemit/xxx/kernel/kernel_patch/`）。新增补丁时注意与已有补丁的上下文冲突。

#### 2.1.3 定制 vendor 目录

`vendor/spacemit/xxx` 目录中主要文件和用途如下：

- `battery`：电池电量曲线配置
- `bluetooth`：蓝牙厂商适配层。PICO 默认适配 RTL8852BS（`rtl8852bs_config`、`rtl8852bs_fw`、`rtkbt.conf`），适配其他蓝牙模组主要修改该文件夹
- `bootanimation_config`：开机动画/音乐/视频配置，参考《系统定制说明》
- `config.json`：该方案包含的组件，可以对组件进行增删和组件属性的增删
- `default_app_config`：默认应用配置
- `etc`：添加一些系统属性，如 `const.product.name="XXX"`，以及 `factorytest_config.json`
- `hals`：目前主要适配音频、编解码通路
- `hdf_config`：方案的 hdf 配置文件（`khdf` 为内核态，`uhdf` 为用户态）
- `image_conf`：各分区镜像的生成参数，如 `system_image_conf.txt` 中的分区大小
- `ohos.build`：添加构建模块
- `power_config`：配置电源管理模式，分为 `NORMAL`，`POWER_SAVE`，`PERFORMANCE`，`EXTREME_POWER_SAVE` 几种，可以配置每种模式的行为，包括关屏时间，待机时间等
- `preinstall-config`：安装的应用 hap 包管理和权限管理
- `product.gni`：一些属性配置
- `resourceschedule`：资源调度配置
- `security_config`：安全相关白名单
- `updater_config`：OTA 升级包配置
- `window_config`：窗口相关配置，比如屏幕 DPI、旋转方向等

#### 2.1.4 定制 device 目录

device 目录包含 board 和 soc 两部分：

- `soc`：针对 K3 芯片平台的适配，是各产品方案通用的部分
- `board`：针对各产品方案的适配，是各产品方案不通用的部分

device 下面的目录结构如下所示（K1 平台的方案列在末尾，便于区分）：

```bash
|-- board
|   `-- spacemit
|       |-- common
|       |-- kernel_patches
|       |-- pico              # K3
|       |-- com260            # K3
|       |-- deb1              # K1
|       |-- cvt               # K1
|       |-- ebag              # K1
|       |-- musepaper         # K1
|       |-- musepaper2        # K1
|       |-- musepaper2-lm     # K1
|       |-- musepi            # K1
|       |-- musepipro         # K1
|       |-- yh001             # K1
|       `-- yh002             # K1
`-- soc
    `-- spacemit
        |-- common
        |-- k1
        `-- k3
```

`device/board/spacemit/xxx` 下面的主要修改点包括：

- `BUILD.gn`：方案的构建入口，聚合 kernel/uboot/opensbi/esos 等子目标
- `cfg/default.para`：一些系统配置参数
- `cfg/fstab.xxx`：文件系统挂载配置
- `cfg/init.xxx.cfg`：启动配置
- `cfg/init.xxx.usb.cfg`：USB 启动配置
- `cfg/gen_insmod_cfg.py`：按 `ko_modules.gni` 生成 init 配置里的 insmod 段
- `kernel`：内核相关的配置和文件
- `kernel/boot`：分区表（`partition_universal.json` 等）和 `bootfs/env_k3.txt`
- `kernel/build_kernel.sh`：内核构建脚本
- `kernel/ko_modules.gni`：需要加载的 ko 清单（唯一来源）
- `kernel/kernel_patch`：板级内核补丁
- `uboot`：U-Boot 构建脚本和板级补丁
- `opensbi`：OpenSBI 构建脚本
- `esos`：ESOS 副核固件构建脚本
- `updater`：升级器分区配置
- `ramdisk_res`：ramdisk 资源
- `wifi` / `audio_alsa` / `audio_drivers` / `camera`：各外设的板级适配

`device/soc/spacemit/k3` 下面的主要修改点包括：

- `hardware`：K3 适配硬件的适配层，包括 camera、codec、display、gpu、isp、omx_il、wifi、firmware 等
- `kernel/boot`：U-Boot 打包配置（`genimage.cfg`、`partition_*.json`、`fastboot.yaml`、`bootctrl.img`）和 boot logo
- `tools`：一些命令行工具，如 `ddr_bw`

### 2.2 通过添加全新方案定制

以新增 K3 方案 `abc` 为例。

#### 2.2.1 定制 U-boot

K3 的 U-Boot 源码在 `extension/k3/uboot-2022.10`，多方案共用。新增方案时：

1. 拷贝板级目录（以 `pico` 为模板）：

   ```bash
   cd device/board/spacemit
   cp -r pico abc
   ```

2. 将 `abc/uboot/uboot_patch/` 下不适用的板级补丁删除，或替换为 `abc` 自己的补丁。脚本会按文件名顺序自动应用该目录下所有 `*.patch`。

3. 由于 `uboot/BUILD.gn` 用的是 `//device/board/$product_company/$product_name/uboot`，目标名 `build_uboot` 在新方案下自动生效，无需改动。

> U-Boot 本身是各方案共用的，通常不需要为新方案准备独立源码。若确实需要，可参考 `extension/k3/uboot-2022.10` 另建目录，并修改 `uboot/BUILD.gn` 中的 `uboot_source_dir`。

#### 2.2.2 定制 Kernel

##### 2.2.2.1 修改 dts

在 `kernel/linux/linux-6.18/arch/riscv/boot/dts/spacemit` 下新增 dts，命名建议为 `k3_abc.dts`（或 `k3-abc.dts`）。添加到上述目录后，在同目录的 `Makefile` 中加入编译项即可。`Makefile` 中 K3 的写法如下：

```bash
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_fpga_1x1.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_evb.dtb k3_evb2-1.dtb k3_evb2-2.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_deb1.dtb k3-pico-itx.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_com260.dtb k3_com260_ifx.dtb k3_com260_ifx2.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3-deepcomputing-fml13v05.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3-firefly-aibox-k3.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_com260_kit_v02.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_gemini_c0.dtb k3_gemini_c1.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_BS01DCMA.dtb
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_com260_tq.dtb k3_com260_ifx_tq.dtb
```

新增时在该组末尾追加：

```bash
dtb-$(CONFIG_SOC_SPACEMIT_K3) += k3_abc.dtb
```

重新编译内核，或者重新编译系统，保险起见，建议删除原来的编译缓存，如下（在源码根目录执行）：

```bash
rm -rf out/kernel

./build.sh --product-name abc --ccache --prebuilt-sdk -T build_kernel
# 或
./build.sh --product-name abc --ccache --prebuilt-sdk
```

最后还需要在板级 `kernel/build_kernel.sh` 中把编译出的 dtb 拷到镜像目录，例如 pico 的写法：

```bash
cp ${KERNEL_BUILD_ROOT}/arch/riscv/boot/dts/spacemit/k3-pico-itx.dtb ${OHOS_IMAGES_DIR}/bootfs/k3-pico-itx.dtb
```

脚本开头还有一个 `KERNEL_DTB` 变量，pico 中仍保留为历史值：

```bash
export KERNEL_DTB=k3_deb1.dtb
```

> 注意：pico 的 `KERNEL_DTB` 没有改成 `k3-pico-itx.dtb`，是因为脚本里实际拷 dtb 用的是单独的 `cp` 行，`KERNEL_DTB` 变量目前在 K3 方案中并未参与拷贝逻辑。新增方案时建议把它一并改成新方案对应的 dtb 名，避免后续脚本逻辑变化时踩坑。

##### 2.2.2.2 修改 defconfig

内核的 defconfig 文件位于：

```bash
kernel/linux/linux-6.18/arch/riscv/configs/k3_bianbu_defconfig
```

该 defconfig 是所有 K3 方案共用的，修改后，对所有的方案生效。

如果只是针对某个特定方案的修改，需要通过 patch 的形式来修改，过程同 2.1.2.2：把 `fix.patch` 放到 `device/board/spacemit/xxx/kernel/kernel_patch`，并在该方案的 `build_kernel.sh` 中打上。

#### 2.2.3 定制 vendor 目录

vendor 目录的定制和前面章节有差别，由于添加的是全新方案，`vendor/spacemit` 下尚无对应目录。定制方法为先拷贝一个现有方案目录，再统一修改方案相关名称，最后进行具体内容的定制。

- 拷贝现有方案：K3 方案建议以 `pico` 为模板：

```bash
cd vendor/spacemit
cp -r pico abc
```

- 统一修改方案名，将所有 `pico` 替换为 `abc`：

```bash
sed -i "s/pico/abc/g" `grep -rl pico ./`
```

- 修改相应文件名：

```bash
find . -name '*pico*'
./etc/param/hardware_pico.para
./etc/param/product_pico.para
./etc/param/product_pico_sys_prod.para

mv ./etc/param/hardware_pico.para ./etc/param/hardware_abc.para
mv ./etc/param/product_pico.para ./etc/param/product_abc.para
mv ./etc/param/product_pico_sys_prod.para ./etc/param/product_abc_sys_prod.para
```

- 删除之前残留的编译缓存，避免编译报错：

```bash
cd abc
rm -f hdf_config/khdf/.built-in.a.cmd hdf_config/khdf/.hdf_hcs_hex.o.d \
      hdf_config/khdf/.modules.order.cmd hdf_config/khdf/built-in.a \
      hdf_config/khdf/hdf_hcs.hcb hdf_config/khdf/hdf_hcs_hex.o \
      hdf_config/khdf/modules.order
```

- 检查 `ohos.build`、`config.json`、`product.gni` 中是否有遗留的 `product_pico` / `device_pico` 字样，一并改为 `abc`。

- 进行修改定制。

#### 2.2.4. 定制 device 目录

device 目录的定制和前面章节有差别，由于添加的是全新方案，`device/board/spacemit` 下尚无对应目录。定制方法为先拷贝一个现有方案目录，再统一修改方案相关名称，最后进行具体内容的定制。

- 拷贝现有方案：K3 方案建议以 `pico` 为模板：

```bash
cd device/board/spacemit
cp -r pico abc
```

- 统一修改方案名：

```bash
sed -i "s/pico/abc/g" `grep -rl pico ./`
```

- 重命名带方案名的文件：

```bash
find . -name '*pico*'
./cfg/fstab.pico
./cfg/init.pico.cfg
./cfg/init.pico.usb.cfg
./updater/config/init.pico.usb.cfg

mv ./cfg/fstab.pico ./cfg/fstab.abc
mv ./cfg/init.pico.cfg ./cfg/init.abc.cfg
mv ./cfg/init.pico.usb.cfg ./cfg/init.abc.usb.cfg
mv ./updater/config/init.pico.usb.cfg ./updater/config/init.abc.usb.cfg
```

- 清理拷贝过来的二进制中间产物（这些文件里同样含有 `pico` 字样，`sed` 处理不到，必须删掉重新生成）：

```bash
rm -f ./audio_drivers/dsp/src/rk3568_dsp_adapter.o ./audio_drivers/dsp/src/rk3568_dsp_ops.o
rm -f ./kernel/ko/*.ko
rm -f ./ramdisk_res/esos.elf ./updater/config/esos.elf
```

> `kernel/ko/` 下的所有 `.ko` 文件（bluetooth.ko、rtw89_8852be.ko 等 30+ 个）都是编译产物，拷贝过来后会带旧方案的符号，直接删掉即可，编译时会从 `out/kernel_ko/` 重新安装。

- 在 `BUILD.gn` 中修改 group 名称（`pico_group` → `abc_group`），并同步修改 `ohos.build` 中的引用。
- **注意**：`kernel/BUILD.gn` 和 `kernel/ko/BUILD.gn` 中 `import("//device/board/spacemit/pico/kernel/ko_modules.gni")` 是**硬编码的 pico 路径**，新方案必须改为 `//device/board/spacemit/abc/kernel/ko_modules.gni`，否则新方案会引用到 pico 的模块清单。

- 在 `kernel/build_kernel.sh` 中更新 `KERNEL_DTB` 和拷贝的 dtb 文件名称，使其与内核对应的 dtb 名称一致。

- 进行修改定制。

#### 2.2.5. build 目录添加权限

- 在 `subsystem_components_whitelist.json` 中添加方案配置（现有 K3 方案为 `device_pico`、`device_com260`）：

```json
"device_abc" :"device_abc",
```

- 在 `compile_standard_whitelist.json` 中添加模块的白名单：搜索该方案拷贝的原方案的名字（如 `pico`），包含 `pico` 的条目都拷贝一份，并将方案名称修改为 `abc`。

- 在 `core/gn/ohos_exec_script_allowlist.gni` 中，参考现有方案（如 `pico`）的写法，添加新方案 `abc` 的脚本路径，确保编译时可正常执行相关脚本：

```bash
"//device/board/spacemit/abc/camera/vdi_impl/v4l2/BUILD.gn",
```

## 1. 调试工具和方法

### 1.1 串口调试

系统默认支持串口调试，波特率为 **115200**。
通过串口可查看 **U-Boot**、**Kernel** 以及 **OpenHarmony init** 进程的相关日志输出。

#### 1.1.1 调整串口打印等级

##### 1.1.1.1 仅本次启动有效

串口中执行如下命令即可：

```bash
echo 8 > /proc/sys/kernel/printk
```

##### 1.1.1.2 持续生效

主要通过修改 `env_k3.txt` 文件中的 `loglevel` 值来实现，有 2 种方式：

1. 修改代码并编译固件

   - 修改 `device/board/spacemit/<board>/kernel/boot/bootfs/env_k3.txt` 中 `loglevel` 的值（`<board>` 为 `pico` 或 `com260`）
   - 重新编译固件并烧录即可
2. 系统中直接修改，按照如下步骤进行：

   - 挂载 bootfs 分区。K3 平台使用 UFS 存储，设备节点为 `/dev/block/sdaX`，没有 `mmcblk*` 设备。bootfs 分区为 `/dev/block/sda1`，也可以直接用符号链接 `/dev/block/by-name/boot`：

   ```bash
   # cd dev/block/
   # ls
   by-name  loop5         sda1        sda3        sda5   sda7   sda9
   loop0    loop6         sda2        sda4        sda6   sda8   platform
   loop1    loop7
   #
   # mount /dev/block/sda1 /tmp
   # cd /tmp
   # ls
   Image  bianbu.bmp  env_k3.txt  k3-pico-itx.dtb  k3_deb1.dtb  lost+found  ramdisk.img
   ```

   - 使用 `busybox vi` 直接编辑 `env_k3.txt`，修改 `loglevel` 的值

   ```bash
   # busybox vi env_k3.txt
   # 按 i 进入编辑模式，修改 loglevel=8
   # 按 ESC 后输入 :wq 保存退出
   ```

   或者使用 `hdc` 工具从主机拉取、修改后再推回：

   ```bash
   D:\>hdc file recv /tmp/env_k3.txt
   FileTransfer finish, Size:156 time:23ms rate:5.83kB/s

   D:\>hdc file send env_k3.txt /tmp/
   FileTransfer finish, Size:156, File count = 1, time:8ms rate:16.75kB/s
   ```

   - 取消挂载 bootfs 分区，重启即可生效（命令是 `umount`，没有 `unmount` 这个命令）

   ```bash
   # umount /tmp
   # reboot
   ```

#### 1.1.2 串口连接方式

K3 平台（`pico`、`com260`）的调试串口固定为 **UART0**，内核控制台参数为 `console=ttyS0,115200`（见 `env_k3.txt` 与 `k3-pico.dtsi` 的 `bootargs`），连接时波特率设置为 **115200**。

##### 1.1.2.1 K3 Pico

接线顺序为 `GND / RX / TX`，注意串口模块的 TX 接开发板 RX、RX 接开发板 TX、GND 共地。
具体引脚位置及板卡框图请参考进迭时空官方硬件文档：[K3 PICO 硬件资源](https://www.spacemit.com/community/document/info?lang=zh&nodepath=ecohardware/k3_series/k3_pico/pico_hw_resources.md)。

##### 1.1.2.2 K3 COM260

COM260 通过板载 `VL817` USB Hub 引出串口，同样按 `GND / RX / TX` 线序连接，波特率 **115200**。
具体引脚位置请参考进迭时空官方硬件文档。

### 1.2 HDC

HDC（Harmony Device Connector）功能类似于 Android 的 ADB，支持 **USB** 和 **TCP** 两种连接模式。
在使用 TCP 模式时，默认端口为 **55555**。
配置文件路径：`device/board/spacemit/xxx/cfg/default.para`
示例如下：

```bash
persist.hdc.mode=usb,tcp
persist.hdc.port=55555
```

### 1.2.1 主机支持 HDC

#### 1.2.1.1 Windows 系统

Windows 系统将 `hdc.exe`（[点我下载](https://archive.spacemit.com/tools/openharmony/hdc.zip)）放在特定目录，并设置环境变量路径。

#### 1.2.1.2 Ubuntu 系统

- 安装依赖项‌：打开终端，输入以下命令来更新软件包列表并安装必要的开发工具和库

  ```bash
  sudo apt-get update
  sudo apt-get install build-essential libstdc++6 libc++1·
  ```
- 下载 HDC 工具包‌：前往 OpenHarmony 官网下载适用于 Linux 平台的最新版 HDC 工具压缩包。将其放置于合适位置后进行解压操作，请根据实际情况调整解压路径

  ```bash
  tar -zxvf hdc_std_<version>_linux.tar.gz -C /opt/hdc/
  ```
- 设置环境变量‌：编辑用户的 shell 初始化脚本（如 `.bashrc`），添加以下行至文件末尾：

  ```bash
  export PATH=$PATH:/opt/hdc/bin
  source ~/.bashrc
  ```
- 验证安装成功与否‌：在新的终端窗口里尝试运行简单的帮助指令以确认一切就绪，如果能够看到详细的帮助文档，则表明整个过程顺利完成

  ```bash
  hdc help
  ```

#### 1.2.2.1 网络连接

需确保 HDC 的服务端和客户端在同一个局域网内，连接方式如下：

```bash
D:\>hdc tconn 10.0.90.142:55555
Connect OK

D:\>hdc shell
#
```

#### 1.2.2.2 USB 连接

```bash

```

#### 1.2.2.3 多设备连接

通过 `-t` 参数指定设备即可，如下：

```bash
D:\>hdc list targets

D:\>hdc -t 0123456789ABCDEF shell
#
```

### 1.7 服务管理

`service_control` 用于启停由 init 托管的 native 服务，服务名即 `/system/etc/init/` 下对应 cfg 文件里定义的 `name`。K3 的音频服务为 `audio_server`（对应 `audio_server.cfg`），K1 上的 `pulseaudio` 在 K3 上**不存在**，执行 `service_control stop pulseaudio` 会静默返回 0 但实际不生效。

<table>
<tbody>
<tr>
<td>命令</td>
<td>用途</td>
</tr>
<tr>
<td>service_control start audio_server</td>
<td>启动音频服务</td>
</tr>
<tr>
<td>service_control stop audio_server</td>
<td>停止音频服务</td>
</tr>
<tr>
<td>service_control</td>
<td>不带参数执行，打印命令用法</td>
</tr>
</tbody>
</table>

查看设备上实际存在哪些服务：

```bash
# 列出所有由 init 托管的服务名
ls /system/etc/init/*.cfg /vendor/etc/init/*.cfg 2>/dev/null

# 查看某个服务当前是否在运行
ps -A -o PID,USER,CMD | grep audio_server
```

> 注意：`service_control` 对**不存在的服务名同样返回 0**，不会报错。因此不能用返回值判断服务是否真的启动成功，必须配合 `ps` 或 `hilog` 确认。

### 1.15 重新挂载 system/vendor 分区为可读写

system/vendor 分区默认挂载为只读（`ro`），当调试的时候需要使用 `hdc file send` 推文件的时候，需要将其重新挂载为可读写，如下：

```bash

```

挂载关系如下（K3 平台使用 UFS，分区设备为 `/dev/block/sdaX`）：

| 分区 | 设备 | 挂载点 | 默认属性 |
|------|------|--------|----------|
| system | `/dev/block/sda6` | `/` | `ro` |

| sys_prod | `/dev/block/sda4` | `/sys_prod` | `ro` |
| chip_prod | `/dev/block/sda5` | `/chip_prod` | `ro` |
| boot | `/dev/block/sda1` | 需手动挂载 | — |
| userdata | `/dev/block/sda9` | `/data` | `rw` |

系统重启后失效，需要重新挂载。

### 1.16 调频

#### 1.16.1 CPU 频率

K3 为 16 核，分为 **2 个 cpufreq policy**，需要分别操作：

| policy | 对应 CPU | 最高频率 |
|--------|----------|----------|
| `policy0` | cpu0 ~ cpu7 | 2200000 kHz（2.2GHz） |
| `policy8` | cpu8 ~ cpu15 | 1800000 kHz（1.8GHz） |

```bash
# 进入 policy0（cpu0~7），policy8 操作方式相同
cd /sys/devices/system/cpu/cpufreq/policy0/

cat scaling_cur_freq
# 查看当前频率

cat scaling_available_frequencies
# 查看可用频率

cat scaling_available_governors
# 查看支持的调频策略

echo userspace > scaling_governor
echo 1600000 > scaling_setspeed
# 调整频率，必须是 scaling_available_frequencies 中列出的值

cat scaling_cur_freq
# 查看调整是否生效
```

`policy0` 可用频率（kHz）：

```
614400 819200 1000000 1100000 1200000 1300000 1400000 1500000
1600000 1700000 1800000 1850000 1900000 2000000 2100000 2150000 2200000
```

`policy8` 可用频率（kHz）：

```
614400 819200 1000000 1100000 1200000 1300000 1400000 1500000 1600000 1700000 1800000
```

> 注意：如果写入的频率不在上表中，内核会**就近向上取整**而不是报错。例如向 `policy0` 写入 `1228800`，实际生效的是 `1300000`。写完务必 `cat scaling_cur_freq` 确认。

#### 1.16.2 DDR 调频

K3（pico / com260）**不支持**通过 `devmem` 直接改写 DDR 频率，K1 方案中 `devmem 0xd4282980` 的用法在 K3 上不适用，原因有两点：

- `0xd4282980` 在 K3 上读出恒为 `0x00000000`，该寄存器不再用于 DDR 频率配置
- 设备上的 `devmem` 来自 toybox，**WIDTH 参数是字节数**（只能是 `1`/`2`/`4`/`8`），`devmem 0xd4282980 32 0xD` 这种写法会直接报 `devmem: bad width: 32`

K3 上可查看的 DDR 相关信息：

```bash
# 查看各 AXI 端口的 DDR 带宽统计（-p 指定端口 0~4 或 all，-t 为轮询间隔 ms）
ddr_bw
ddr_bw -p all -t 1000

# 查看 DDR 容量与占用
free -h
cat /proc/meminfo

# 查看 DDR 起始地址与大小
cat /proc/device-tree/memory@*/reg | od -An -tx1
```

如确需调整 DDR 频率，请在 U-Boot 阶段（`device/board/spacemit/<board>/uboot/uboot_patch/0002-ddr-lpddr5-slim.patch` 所在仓库）修改 DDR 初始化参数并重新烧写，系统起来后不再提供运行时调频入口。

## 3. 常见问题调试手段

### 3.1 外设

#### 3.1.1 屏幕背光无法调节

背光调节只对板载 eDP/MIPI 面板有效。先确认当前接的是哪种屏：

```bash
# cat /sys/class/drm/card*-*/status 对应连接器
# for c in /sys/class/drm/card*-*/status; do echo $c: $(cat $c); done
/sys/class/drm/card1-eDP-1/status: disconnected
/sys/class/drm/card2-DP-1/status: connected
```

- **外接 DP/HDMI 显示器**：亮度由显示器自身控制（显示器菜单按键），系统**无法调节**。此时 `power-shell display -s xxx` 会返回 `Set brightness to xxx failed`，属于正常现象，不是问题
  - `/sys/class/backlight/backlight` 节点仍然存在，但它对应的是 eDP 面板的 PWM 背光，与 DP 显示器无关。eDP 未连接时 `bl_power` 为 `4`（关闭），往 `brightness` 写值虽然能写进去，屏幕亮度不会变化
- **eDP 面板**：按以下步骤排查
  - 通过查看和设置节点 `/sys/class/backlight/backlight/brightness` 确认驱动是否正常（`max_brightness` 为 `255`）
    - 直接写入节点验证驱动：`echo 200 > /sys/class/backlight/backlight/brightness`
  - 如果设置上述节点亮度无变化，说明驱动存在问题，需要查驱动，重点查看背光对应的 PWM 是否正常工作，以及 `bl_power` 是否为 `0`（开启）
  - 如果设置上述节点亮度有变化，说明是 OH 上层的问题。上层用 `power-shell display -s <value>` 设置，`value` 取值 `1 ~ 255`
  - 查看上层显示电源服务记录的亮度状态：

    ```bash
    # hidumper -s 3308 -a -a | grep -iE "bright|state"
    Display Id=0 State=0 Discount=1.000000 Brightness=255
    DeviceBrightness=255
    Brightness Limits: Max=255 Min=1 Default=102
    ```

### 3.2 系统

#### 3.2.1 替换内核

- 挂载 bootfs 分区，可替换 `Image`、`ramdisk.img` 和 `.dtb` 文件

K3 平台的两个方案对应的 dtb 如下（`dtb` 文件名不同方案不一样）：

| 方案 | dtb 文件 | 内核源码 dts |
|------|----------|--------------|
| K3 Pico | `k3-pico-itx.dtb` | `k3-pico-itx.dts`（引用 `k3-pico.dtsi`） |
| K3 COM260 | `k3_com260.dtb`（另有 `k3_com260_kit_v02.dtb`、`k3_com260_ifx.dtb`） | `k3_com260.dts` |

```bash

# ls
by-name  loop5         sda1        sda3        sda5   sda7   sda9
loop0    loop6         sda2        sda4        sda6   sda8   platform

# mount /dev/block/sda1 /tmp
# cd /tmp
# ls

```

> 说明：bootfs 分区内实际内容以编译产物为准。上例为 pico 的 bootfs 内容；com260 下对应为 `k3_com260.dtb` 等，`env_k3.txt` 相同。

- 通过 `hdc` 将更新的内核或者 `dtb` 文件推入 `/tmp` 文件夹

```bash
D:\>hdc file send Image /tmp/
D:\>hdc file send k3-pico-itx.dtb /tmp/     # com260 方案换成 k3_com260.dtb
```

- 取消挂载 bootfs 分区，重启即可生效

```bash
# umount /tmp
# reboot
```

> 注意：
>
> - 内核镜像文件名是 `Image`（不是 `Image.itb`），启动参数 `knl_name=Image` 见 `env_k3.txt`
> - `ramdisk.img` 也在 bootfs 分区内，替换内核时若 initramfs 与内核不匹配，需要一并替换
> - 替换后若设备无法启动，可通过串口进入 U-Boot 后重新烧写 bootfs 分区恢复

#### 3.2.2 进入 U-Boot

- 连接串口，关机后，串口输入按住 s 键，上电开机，进入 U-Boot

> 说明：K3 当前固件的 init 配置（`/system/etc/init/init.reboot.cfg`）中只有 `reboot` 和 `suspend` 两个 job，没有 `uboot` 目标；U-Boot 补丁（`device/board/spacemit/pico/uboot/uboot_patch/0001-uboot.patch`）也只处理了 `BOOT_MODE_USB` 和 `BOOT_MODE_UPDATER`。因此 `reboot uboot` 在 K3 上不可用，请使用串口按住 s 键的方式进入 U-Boot。

##### 3.2.3.1 常规 cppcrash 处理方法

   --- a/k3/tools/ddr_bw/BUILD.gn
   +++ b/k3/tools/ddr_bw/BUILD.gn
   @@ -6,6 +6,7 @@ cflags_c_common = [
      "-Wno-unused-function",
      "-Wno-pointer-to-int-cast",
      "-Wno-deprecated-non-prototype",
   +  "-O0",
    ]

    cflags_cc_common = [
   @@ -13,6 +14,7 @@ cflags_cc_common = [
      "-Wno-unused-function",
      "-Wno-pointer-to-int-cast",
      "-Wno-deprecated-non-prototype",

#### 3.2.4 打印堆栈

在调试或者跟踪代码的时候，经常需要打印函数调用栈，可以通过调用 `printCallers` 接口来实现，具体的接口如下：

```cpp
#include <execinfo.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#define MAX_FRAMES 20
void printCallers()
{
    int layers = 0, i = 0;
    char ** symbols = NULL;
    
    void * frames[MAX_FRAMES];
    memset(frames, 0, sizeof(frames));
    layers = backtrace(frames, MAX_FRAMES);
    for (i=0; i<layers; i++) {
        printf("Layer %d: %p\n", i, frames[i]);
    }
    printf("------------------\n");
    
    symbols = backtrace_symbols(frames, layers);
    if (symbols) {
        for (i=0; i<layers; i++) {
            printf("SYMBOL layer %d: %s\n", i, symbols[i]);
        }
         free(symbols);
    }
    else {
        printf("Failed to parse function names\n");
    }
}
```

将上面的接口放入要打印堆栈的文件中，调用 `printCallers` 进行打印即可。

### 3.3 休眠唤醒异常

#### 3.3.1 只关屏，无法深度休眠

- 查看 `vendor/spacemit/pico/power_config/power_mode_config.xml`（com260 对应 `vendor/spacemit/com260/power_config/`）是否设置了禁止深度休眠，具体参考 K3 OH6.1 系统定制说明 的电源管理定制章节
  - 该文件按电源模式（`600`~`603`）配置 `DisplayOffTime(101)`、`SystemAutoSleepTime(102)` 等开关，取值 `-1` 表示不超时/不生效。例如 pico 的 `600` 模式 `DisplayOffTime = -1`，即不自动息屏，看上去像"关屏后不休眠"
- 通过 `power-shell dump -a` 查看系统是否拿了禁止休眠锁
- 查看 hilog 和内核 log 是否有异常打印

#### 3.3.2 深度休眠失败

现象：系统已发起休眠（`PM: suspend entry (deep)`），但中途中止并立即返回，没有真正进入深度休眠。

1. 查看休眠统计，确认失败在哪一步、哪个设备

```bash
cd /sys/power/suspend_stats
for f in *; do echo "$f: $(cat $f)"; done
```

重点关注 `fail`（失败次数）、`last_failed_step`（失败阶段，如 `freeze`、`suspend`、`suspend_noirq`）、`last_failed_dev`（失败的设备）、`last_failed_errno`（错误码）。

2. 查看是否有唤醒源或唤醒锁阻止休眠

```bash
cat /sys/kernel/debug/wakeup_sources    # active_since 不为 0 的即当前持有中
cat /sys/power/wake_lock                # 用户态持有的内核唤醒锁
power-shell dump -a                     # OH 系统层的 RunningLock
```

3. 打开休眠调试 log 后重新休眠

```bash
echo 9 > /proc/sys/kernel/printk
echo N > /sys/module/printk/parameters/console_suspend
echo 1 > /sys/power/pm_debug_messages
echo 1 > /sys/power/pm_print_times      # 打印每个设备 suspend/resume 耗时
echo +20 > /sys/class/rtc/rtc0/wakealarm
echo mem > /sys/power/state
dmesg | grep -E "PM:|Freezing|failed|abort"
```

常见失败打印：

| 打印 | 原因 |
|------|------|
| `Freezing of tasks failed` | 有进程/内核线程无法冻结，log 中会列出对应任务 |
| `PM: dpm_run_callback(): xxx returns -xx` / `PM: Device xxx failed to suspend` | 某个驱动的 suspend 回调返回错误 |
| `PM: Some devices failed to suspend, or early wake event detected` | 设备休眠失败或休眠过程中有唤醒事件 |
| `PM: Wakeup pending, aborting suspend` / `active wakeup source: xxx` | 有唤醒源处于激活状态，休眠被中止 |

4. 用 `pm_test` 分阶段定位

`pm_test` 让休眠流程只走到指定阶段，等待 5 秒后自动返回，不会真正掉电，可以逐级缩小问题范围：

```bash
cat /sys/power/pm_test                  # [none] core processors platform devices freezer
echo freezer > /sys/power/pm_test       # 只测试进程冻结
echo mem > /sys/power/state
echo devices > /sys/power/pm_test       # 测试到设备 suspend
echo mem > /sys/power/state
echo none > /sys/power/pm_test          # 测试完恢复
```

按 `freezer` → `devices` → `platform` → `processors` → `core` 的顺序依次测试，第一个失败的阶段就是问题所在。

> 注意：从 `devices` 级别开始 USB 控制器会被 suspend，hdc 连接会断开约 10~20 秒后自动恢复，命令输出会丢失。通过 hdc 调试时，建议把测试写成脚本后台执行，结果写到文件，重连后再查看：
>
> ```bash
> cat > /data/local/tmp/pmt.sh <<'EOF'
> echo devices > /sys/power/pm_test
> echo mem > /sys/power/state; echo rc=$? > /data/local/tmp/pmt.log
> echo none > /sys/power/pm_test
> dmesg > /data/local/tmp/pmt.dmesg
> EOF
> nohup sh /data/local/tmp/pmt.sh > /dev/null 2>&1 &
> ```

5. 确认是否真正进入了深度休眠

`echo mem > /sys/power/state` 返回 0 不代表一定睡下去了，以 dmesg 中的以下打印为准：

```text
PM: suspend entry (deep)
PM: suspend of devices complete after 702.014 msecs
Disabling non-boot CPUs ...
Timekeeping suspended for 18.464 seconds      # 有这行才说明真正进入了深度休眠
PM: suspend exit
```

同时 `/sys/power/suspend_stats/success` 会加 1，`/sys/power/pm_wakeup_irq` 为本次唤醒的中断号（rtc 唤醒时可在 `/proc/interrupts` 中对应查到）。开启 `pm_print_times` 后，可用下面的命令找出 suspend/resume 耗时超过 100ms 的设备：

```bash
dmesg | grep -E "returned [-0-9]+ after [0-9]{6,} usecs"
```

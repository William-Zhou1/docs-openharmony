## 2. 添加定制方案

产品方案定制涉及以下核心代码仓库：

- `build`：添加构建白名单，主要修改文件为：

  - `subsystem_components_whitelist.json`（注意实际文件名是 `components`，不是 `compoents`）
  - `compile_standard_whitelist.json`
  - `core/gn/ohos_exec_script_allowlist.gni`
- `vendor/spacemit`：进迭厂商定制适配目录
- `device/board/spacemit`：进迭厂商板级适配目录
- `device/soc/spacemit`：进迭厂商芯片适配目录
- `kernel/linux/spacemit_kernel-6.6`：进迭厂商内核
- `extension/k1`：K1 的 U-Boot、OpenSBI 源码

添加定制方案通过以下两种方式实现：

- **通过修改现有方案进行定制**
  适用于在现有开发板基础上快速适配新的方案。K1 平台现有 `musepaper2`、`musepaper`、`musepipro`、`deb1`、`cvt`、`ebag`、`musepi`、`musepaper2-lm`、`yh001`、`yh002` 等方案，可通过修改其中的参数来支持新的开发板。

  - 适配流程简单，开发速度快。
  - 注意：新开发板的板号需与原开发板保持一致（例如，仍命名为 `deb1`）。
- **通过添加全新方案定制**
  适用于需要完全独立配置的场景。

  - 前期需进行一定的适配工作。
  - 不会与现有开发板配置冲突，可灵活进行自定义和修改。

下面分别对两种定制方案的操作进行说明：

### 2.1 通过修改现有方案定制

#### 2.1.1 定制 U-Boot

K1 的 U-Boot 和 OpenSBI 都是**源码编译**的，源码就在仓库里，不需要向进迭时空索要 bin 文件：

- U-Boot 源码：`extension/k1/uboot-2022.10`
- OpenSBI 源码：`extension/k1/opensbi`
- 板级构建入口：`device/board/spacemit/xxx/uboot/BUILD.gn`（`action("build_uboot")`）与 `device/board/spacemit/xxx/opensbi/BUILD.gn`
- 构建脚本：`device/board/spacemit/xxx/uboot/build_uboot.sh`、`device/board/spacemit/xxx/opensbi/build_opensbi.sh`
- 板级补丁：`device/board/spacemit/xxx/uboot/uboot_patch/*.patch`（`build_uboot.sh` 会按顺序应用该目录下所有 `*.patch`）

`build_uboot.sh` 的流程是：把 U-Boot 源码拷到 `out/uboot-k1` → 依次打 `uboot_patch` 下的补丁 → 编译 → 把产物拷到镜像输出目录。`build_opensbi.sh` 类似，构建目录是 `out/opensbi-k1`。

编译产物及去向：

| 产物 | 去向 |
|------|------|
| `u-boot.itb` | `${OHOS_IMAGES_DIR}/u-boot.itb` |
| `FSBL.bin` | `${OHOS_IMAGES_DIR}/factory/FSBL.bin` |
| `bootinfo_*.bin` | `${OHOS_IMAGES_DIR}/factory/` |
| `env.bin` | `${OHOS_IMAGES_DIR}/env.bin` |
| `fw_dynamic.itb`（OpenSBI） | `${OHOS_IMAGES_DIR}/fw_dynamic.itb` |

> 注意：上述 U-Boot / OpenSBI 产物**全部在构建时从源码生成，不回拷源码树**。旧版本文档里「`u-boot.itb`、`fw_dynamic.itb`、`env.bin` 由 `build_kernel.sh` 从 `device/soc/spacemit/k1/kernel/boot/` 拷贝」的说明已经过时：`build_kernel.sh` 中对应的三行 `cp` 已被注释掉，改为由板级 `build_uboot` / `build_opensbi` 两个 action 产出。

源码树中与之相关、仍由 `build_kernel.sh` 拷贝到打包目录的是打包配置和启动环境文件。`device/soc/spacemit/k1/kernel/boot/` 目录如下：

```bash
|-- bootctrl.img
|-- bootfs
|   |-- bmp2ppm.sh
|   |-- boot_logo_bzqt_0.bmp
|   |-- boot_logo_spacemit_0.bmp
|   |-- boot_logo_spacemit_180.bmp
|   |-- boot_logo_spacemit_270.bmp
|   |-- boot_logo_spacemit_90.bmp
|   `-- boot_logo_zkhl_0.bmp
|-- env.bin
|-- factory
|   |-- bootinfo_emmc.bin
|   |-- bootinfo_sd.bin
|   |-- bootinfo_spinand.bin
|   |-- bootinfo_spinor.bin
|   `-- FSBL.bin
|-- fastboot.yaml
|-- fw_dynamic.itb
|-- genimage.cfg
|-- partition_2M.json
|-- partition_flash.json
`-- u-boot.itb
```

`build_kernel.sh` 中的拷贝示例如下（**注意：`env.bin` / `u-boot.itb` / `fw_dynamic.itb` 这三行在当前脚本中是注释状态**，实际由 `build_uboot` / `build_opensbi` 产出）：

```bash

cp ${OHOS_SOURCE_ROOT}/device/board/${DEVICE_BOARD}/${DEVICE_NAME}/kernel/boot/bootfs/env_k1-x.txt ${OHOS_IMAGES_DIR}/bootfs/env_k1-x.txt
cp ${OHOS_SOURCE_ROOT}/device/board/${DEVICE_BOARD}/${DEVICE_NAME}/kernel/boot/partition_universal.json ${OHOS_IMAGES_DIR}/partition_universal.json
cp ${OHOS_SOURCE_ROOT}/device/soc/${DEVICE_BOARD}/k1/kernel/boot/fastboot.yaml ${OHOS_IMAGES_DIR}/fastboot.yaml
cp ${OHOS_SOURCE_ROOT}/device/soc/${DEVICE_BOARD}/k1/kernel/boot/genimage.cfg ${OHOS_IMAGES_DIR}/genimage.cfg
cp ${OHOS_SOURCE_ROOT}/device/soc/${DEVICE_BOARD}/k1/kernel/boot/bootctrl.img ${OHOS_IMAGES_DIR}/bootctrl.img
cp ${OHOS_SOURCE_ROOT}/device/soc/${DEVICE_BOARD}/k1/kernel/boot/partition_2M.json ${OHOS_IMAGES_DIR}/partition_2M.json
cp ${OHOS_SOURCE_ROOT}/device/soc/${DEVICE_BOARD}/k1/kernel/boot/partition_flash.json ${OHOS_IMAGES_DIR}/partition_flash.json
```

各方案的 U-Boot 启动环境文件位于板级目录：

`device/board/spacemit/xxx/kernel/boot/bootfs/env_k1-x.txt`

```bash
// Common parameter
console=ttyS0,115200
init=/init
bootdelay=0
loglevel=1
default_boot_device=soc/d4281000.sdh
boothardware=musepaper2
```

若某一方案需要专属的 U-Boot 行为，优先在 `device/board/spacemit/xxx/uboot/uboot_patch/` 下新增补丁，而不是直接改 `extension/k1/uboot-2022.10` 源码。

##### 2.1.2.2 修改 defconfig

内核的 defconfig 文件位于：

```bash
kernel/linux/spacemit_kernel-6.6/arch/riscv/configs/k1_defconfig
```

该 defconfig 是所有方案共用的，修改后，对所有的方案生效。

如果只是针对某个特定方案的修改，需要通过 patch 的形式来修改，过程如下：

- 生成 patch：`fix.patch`
- 将生成的 `fix.patch` 放置于 `device/board/spacemit/xxx/kernel/kernel_patch` 中
- `device/board/spacemit/xxx/kernel/build_kernel.sh` 中打 patch，如下：

```bash
patch -p1 <${OHOS_SOURCE_ROOT}/device/board/${DEVICE_BOARD}/${DEVICE_NAME}/kernel/kernel_patch/fix.patch
```

#### 2.1.3 定制 vendor 目录

`vendor/spacemit/xxx` 目录中主要文件和用途如下：

- `battery`：电池电量曲线配置（部分方案有）
- `bluetooth`：蓝牙厂商适配层。K1 各方案默认适配 RTL8852BS（`rtl8852bs_config`、`rtl8852bs_fw`、`rtkbt.conf`），适配其他蓝牙模组主要修改该文件夹
- `bootanimation_config`：开机动画/音乐/视频配置，参考《系统定制说明》
- `config.json`：该方案包含的组件，可以对组件进行增删和组件属性的增删
- `default_app_config`：默认应用配置
- `etc`：添加一些系统属性，如 `const.product.name="XXX"`；`etc/param/` 下是 `product_<product>.para`、`hardware_<product>.para` 等参数文件
- `hals`：目前主要适配音频、编解码通路
- `hdf_config`：方案的 hdf 配置文件（`khdf` 为内核态，`uhdf` 为用户态）
- `image_conf`：各分区镜像的生成参数，如 `system_image_conf.txt` 中的分区大小
- `ohos.build`：添加构建模块
- `power_config`：配置电源管理模式，分为 `NORMAL`，`POWER_SAVE`，`PERFORMANCE`，`EXTREME_POWER_SAVE` 几种，可以配置每种模式的行为，包括关屏时间，待机时间等
- `preinstall-config`：安装的应用 hap 包管理和权限管理（`install_list.json`、`install_list_capability.json`、`install_list_permissions.json`）
- `product.gni`：一些属性配置
- `resourceschedule`：资源调度配置
- `security_config`：安全相关白名单
- `window_config`：窗口相关配置，比如屏幕 DPI、旋转方向、过场动画时间配置等

> 注意：OTA 的升级包配置（`BOARD.list`、`VERSION.mbn`、`updater_specified_config_*.xml`）**不在** vendor 目录下，而在板级目录 `device/board/spacemit/xxx/updater/updater_config/`。vendor 下的 `updater_config/build_cfg.gni` 只是预留文件。

- soc：针对 K1 芯片平台的适配，是各产品方案通用的部分

`device/board/spacemit/xxx` 下面的主要修改点包括：

- `BUILD.gn`：方案的构建入口，聚合 kernel/uboot/opensbi 等子目标
- `cfg/default.para`：一些系统配置参数
- `cfg/fstab.xxx`：文件系统挂载配置
- `cfg/init.xxx.cfg`：启动配置
- `cfg/init.xxx.usb.cfg`：USB 启动配置
- `kernel`：内核相关的配置和文件
- `kernel/boot`：分区表（`partition_universal.json` 等）和 `bootfs/env_k1-x.txt`

- `uboot`：U-Boot 构建脚本和板级补丁
- `opensbi`：OpenSBI 构建脚本
- `updater`：升级器分区配置（`updater_config/` 为 OTA 包配置）

- `wifi` / `audio_alsa` / `audio_drivers` / `camera` / `distributedhardware`：各外设的板级适配

`device/soc/spacemit/k1` 下面的主要修改点包括：

- `hardware`：K1 适配硬件的适配层，包括硬件编解码，GPU、display、camera 等
- `kernel/boot`：U-Boot 打包配置（`genimage.cfg`、`partition_*.json`、`fastboot.yaml`、`bootctrl.img`）和 boot logo
- `tools`：一些命令行工具，如 `ddr_bw`

### 2.2 通过添加全新方案定制

#### 2.2.1 定制 U-boot

K1 的 U-Boot/OpenSBI 源码在 `extension/k1/uboot-2022.10` 与 `extension/k1/opensbi`，各方案共用，新增方案时：

1. 拷贝板级目录（以 `musepaper2` 为模板）：

   ```bash
   cd device/board/spacemit
   cp -r musepaper2 abc
   ```

2. `abc/uboot/uboot_patch/` 默认是空的（只有 `.gitkeep`）。如需方案专属的 U-Boot 行为，在该目录下新增 `0001-xxx.patch`，`build_uboot.sh` 会按文件名顺序自动应用全部 `*.patch`。

3. `abc/opensbi/` 目录复制过来即可，`build_opensbi.sh` 不需要按方案改名。

4. `uboot/BUILD.gn` 用的是 `//device/board/$product_company/$product_name/uboot`，目标名 `build_uboot` 在新方案下自动生效，无需改动。

> 各方案的 U-Boot 启动环境文件是板级的 `device/board/spacemit/xxx/kernel/boot/bootfs/env_k1-x.txt`，新增方案时按新方案修改其中的 `boothardware`、`default_boot_device` 等值。分区表 `partition_universal.json` / `partition_universal_ab.json` 同样在 `device/board/spacemit/xxx/kernel/boot/` 下。

##### 2.2.2.2 修改 defconfig

内核的 defconfig 文件位于：

```bash
kernel/linux/spacemit_kernel-6.6/arch/riscv/configs/k1_defconfig
```

该 defconfig 是所有方案共用的，修改后，对所有的方案生效。

如果只是针对某个特定方案的修改，需要通过 patch 的形式来修改，过程如下：

- 生成 patch：`fix.patch`
- 将生成的 `fix.patch` 放置于 `device/board/spacemit/xxx/kernel/kernel_patch` 中
- `device/board/spacemit/xxx/kernel/build_kernel.sh` 中打 patch，如下：

```bash
patch -p1 <${OHOS_SOURCE_ROOT}/device/board/${DEVICE_BOARD}/${DEVICE_NAME}/kernel/kernel_patch/fix.patch
```

#### 2.2.3 定制 vendor 目录

vendor 目录的定制和前面章节有差别，由于添加的是全新方案，`vendor/spacemit` 下尚无对应目录。定制方法为先拷贝一个现有方案目录，再统一修改方案相关名称，最后进行具体内容的定制。

- 拷贝现有方案：选择一个相似的方案进行拷贝，例如要适配开发板，可选择 `deb1`；要适配平板，可选择 `musepaper`。新建方案以开发板 abc 为例，如下：

```bash
cd vendor/spacemit
cp -r deb1 abc
```

- 统一修改方案名，将所有 `deb1` 替换为 `abc`，并修改相应文件名：

```bash
# sed -i "s/deb1/abc/g" `grep -rl deb1 ./`
# find . -name *deb1*
./etc/param/product_deb1.para
./etc/param/hardware_deb1.para
# mv ./etc/param/product_deb1.para ./etc/param/product_abc.para
# mv ./etc/param/hardware_deb1.para ./etc/param/hardware_abc.para
```

- 删除之前的编译缓存避免编译报错）：

```bash
cd abc
rm hdf_config/khdf/.built-in.a.cmd hdf_config/khdf/.hdf_hcs_hex.o.d hdf_config/khdf/.modules.order.cmd hdf_config/khdf/built-in.a hdf_config/khdf/hdf_hcs.hcb hdf_config/khdf/hdf_hcs_hex.o hdf_config/khdf/modules.order
```

- 进行修改定制。

#### 2.2.4. 定制 device 目录

device 目录的定制和前面章节有差别，由于添加的是全新方案，`device/board/spacemit` 下尚无对应目录。定制方法为先拷贝一个现有方案目录，再统一修改方案相关名称，最后进行具体内容的定制。

- 拷贝现有方案：选择一个相似的方案进行拷贝，例如要适配开发板，可选择 `deb1`；要适配平板，可选择 `musepaper`。新建方案以开发板 abc 为例，如下：

- 统一修改方案名，将所有 `deb1` 替换为 `abc`，并重命名相关文件：

#### 2.2.5. build 目录添加权限

- 在 `build/subsystem_components_whitelist.json` 中添加方案配置（注意实际文件名是 `components`，不是 `compoents`）。该文件是一层扁平的 `"key":"value"` 映射，现有 K1 方案的条目类似 `"device_musepaper2" :"device_musepaper2"`，新增一行即可：

```json
  "device_abc" :"device_abc",
```

- 在 `build/compile_standard_whitelist.json` 中添加模块的白名单：搜索该方案拷贝的原方案的名字，比如 `deb1`，包含 `deb1` 的模块都拷贝一份，并将方案名称修改为 `abc`
- 在 `build/core/gn/ohos_exec_script_allowlist.gni` 中，参考现有方案的写法，添加新方案 `abc` 的脚本路径，确保编译时可正常执行相关脚本。K1 各方案目前都只登记了 camera 的 `v4l2` 一项，例如：

```bash
"//device/board/spacemit/musepaper2/camera/vdi_impl/v4l2/BUILD.gn",
```

所以新方案至少要加：

```bash
"//device/board/spacemit/abc/camera/vdi_impl/v4l2/BUILD.gn",
```
